# Decisions

## 2026-11-15 — Link previews: one static preview, plus a snapshot maker in Delen (W29)

- **Why no preview per link.** The site is static (GitHub Pages) and a share link keeps its state in the `#hash`. Link crawlers (WhatsApp, LinkedIn, Slack, iMessage, X) fetch the URL without the hash (browsers never send it) and run no JavaScript, so they all read the same `index.html` head. A per-link `og:image` needs something on the server that sees the state and answers with other tags and another image; static hosting cannot do that.
- **Static preview** in `index.html`: description, canonical, `og:*` (type, site_name, locale nl_NL, url, title, description, image + type/size/alt) and `twitter:card summary_large_image`. The image is `assets/og-image.png` (1200×630, committed), made by `node scripts/build-og-image.mjs`: brand-dark #111923, Rotterdam green, the logo, title, subtitle, site address and a stylised hex "map" in the Woonscore greens. No dependency: the script reads glyph outlines from DejaVu Sans on the build machine (`FONT_REGULAR`/`FONT_BOLD` override the path), flattens them to polygons and fills them with a small scanline rasteriser; PNG encoding is `build-brand-assets.mjs`'s `encodePng` (now with an optional height). The og URLs are absolute to the Pages address; a move to another host must change them.
- **Snapshot maker** ("Maak afbeelding" in the Delen dialog): renders the current view as a 1200×630 PNG in the browser, previewed in the dialog. Then "Delen met afbeelding" where the Web Share API can share files (`navigator.canShare({ files })`; shares the PNG with the link as `text`, because Android drops `url` when files are present), else "Download PNG"; the link button stays as it was. This is the way to get the real view into a chat: the app sends the picture itself instead of the crawler.
- **How the map gets into the picture.** The map is Leaflet: the dark/light basemaps are a MapLibre GL canvas inside Leaflet (maplibre-gl-leaflet), the aerial photo is `<img>` tiles, the choropleth is Leaflet SVG. The GL canvas is copied inside its own `render` event after `triggerRepaint()` (the buffer is valid then), so no `preserveDrawingBuffer` and no cost per frame; tiles are drawn at their screen rectangles (the aerial `tileLayer` now asks `crossOrigin: 'anonymous'`; PDOK and OpenFreeMap send CORS headers); the overlay SVG is serialised to an image. Labels and markers (DOM) are not drawn. If the canvas is tainted anyway, the image falls back to the card without the map. Dashboard and Ranglijst get the card without a map, with the view name.
- **What the image shows**: logo, "Roffatistics", the legend title (layer), the selected area's name (only when "Geselecteerd gebied" is ticked), the legend colours with the first/last class bound, and host + path of the site (never the `#state`). No wizard answers ever. A personal Woonscore map ("jouw wensen") is drawn only when the answers are ticked and every sensitive part they hold (herkomst, opleiding, inkomen) is ticked too, because its colours follow from those answers; otherwise the image is the card with "Woonscore" and no map or legend (`personalMapAllowed`).
- **Code**: pure helpers in `modules/snapshot.js` (file name `roffatistics-<layer>-<area>.png`, `canShareFiles`, `fitText`/`fitSize`, `coverCrop`, `snapshotLayout`, `personalMapAllowed`; `tests/snapshot.test.js`); canvas work in `modules/snapshot-render.js`, loaded on demand; buttons in `share-dialog.js`; `getBasemapGL()` in map.js. Unverified in a browser (no browser runs by agents): the GL grab, SVG overlay alignment during pan/zoom animation, font metrics of the card.
- **Later, if per-link previews are wanted:** a tiny server or edge worker (Cloudflare Worker, a Hermes container) in front of the site that takes the state as a *query string* (`/s?ds=woonscore&area=WK059901`, which crawlers do see), answers crawlers with `og:*` tags pointing at an image it renders for that state (e.g. with resvg/satori or a headless browser, cached), and redirects people to the `#hash` link. The share dialog would then hand out that URL instead.

- **Problem:** the linear min→max ramp let a few public-space areas (buurt crime per 1.000 up to 738, Zuidplein) squeeze everything else into the bottom fifth: 26 and 85 got nearly the same colour.
- **One pure module `modules/scale.js`:** `buildScale(values, { method })` returns `colorFor`, `classOf`, `isOutlier`/`outlierSide`, `classes`, `breaks`, `median`, `q1`, `q3`, `lo`/`hi` (fences) and `outliers` counts. Map (Rotterdam wijk/buurt and the Nederland tiers), legend, Ranglijst bars/chips and dashboard bars/dots all use it, built from exactly the set on screen (scope, level/tier and crime mode), so every toggle rebuilds it. `interpolateColor` moved there (re-exported by overlays.js), as did `NO_DATA_COLOR` (re-exported by rotterdam.js).
- **Default 'quantile': 7 stepped classes** on the existing purple→orange ramp, thresholds at the 1/7…6/7 quantiles (type-7 interpolation), so classes are evenly filled and the median lands in the middle class. Stepped classes read better on a map than a continuous ramp and can be listed in the legend. Ties never leave an empty class (empty classes are merged and the remaining colours spread over the whole ramp); ≤ 7 distinct values get one class per value; a constant set is one middle-colour class. **'linear'** keeps the old continuous ramp for comparison.
- **Outliers: Tukey fences (1.5·IQR) on the raw values and, when nothing is negative, on log1p(values); an outlier must be outside both** (the wider fence per side). Raw Tukey alone flags 11 of 76 buurten for crime per 1.000 (everything above ~130, a normal right tail); log alone flags the lowest buurt (23) as a low outlier, because log stretches small values. Together they flag the 6 public-space buurten (Zuiderpark 349, Charlois Zuidrand 449, Cs Kwartier 471, Cool 502, Dijkzigt 509, Zuidplein 738; fence 182) and, at wijk level, Rotterdam Centrum (231). Absolute counts and density flag nothing (buurten with 0 crimes widen the log fence; the quantile classes already handle the spread). A raw IQR of 0 or ≤ 7 distinct values flags nothing. Outliers keep their class fill (the top or bottom class) and add a solid red border `#ef4444`, weight 2.5: solid reads better than dashed on small buurt polygons over the dark basemap. ## 2026-11-15 — Area search

- **Own matcher, no dependency** (`modules/fuzzy.js`, pure). ## 2026-11-15 — Woonscore (Epic W1, v0.18.0)

- **Engine** `modules/score.js` (pure, no imports): percentile 0..1 within peers (mid-rank, same rule as `ranking.js`), preference `higher`/`lower`/`target` (Gaussian with sd = tolerance, shifted to reach exactly 0 at ±2 tolerances), `filter` flags an area (`filtered`) and never drops it, score = 100 × Σ w·f / Σ w over factors with data, null below 60 % weight coverage, `explain()` = plus/minus factors by impact 100·w·(f − 0.5)/Σw (above or below the peer middle).
- **log1p:** a percentile rank is unchanged by a monotone transform, so log1p before the percentile (plan §1) changes nothing; the `log` flag is kept and matters only for `target` distances. Shrinkage works on raw rates.
- **Shrinkage** only for buurten (parent = wijk) and only on rates per 1.000 (`RATE_KEYS`: crime, bijstand): rate' = w·rate + (1 − w)·wijk, w = n/(n + 300), applied to every buurt (proper empirical Bayes; large buurten barely move). The "weinig inwoners" badge shows when n < 300, i.e. when the wijk weighs more than the buurt. Wijken and NL gemeenten are not shrunk. The shown values stay the raw rates; only the score uses the shrunk ones.
- **Standaard preset** (`modules/presets.js`): a theme weight (35/20/25/10/10) is split evenly over the theme's metrics that have data among the peers; a theme without data is dropped and the rest renormalise. So NL gemeenten (crimeRate, avgIncome, highEdu) get veiligheid 35/65, welvaart 20/65, opleiding 10/65 instead of the crime metric collapsing to one fifth of 35. `ownerOccupiedPct` counts as a mild plus here although it is neutral as a layer.
- **Gelijk gewogen preset** = weight 1 for every directional `inOverall` dataset, no shrinkage, no coverage threshold; tested to equal the Ranglijst Totaalscore. The Totaalscore code (`ranking.scoreAreas`, `area-detail.overallRank`) is left as it is rather than rerouted, so its crime-mode (`abs`) behaviour and the used/possible counter stay unchanged.
- **Where the score is computed:** `areas.js` adds `values.woonscore` and the full result (`area.woonscore`) to wijken and buurten at load; `app.js` adds `woonscore` to the province and gemeente rows after each CBS merge. The Woonscore always uses rates, also in crime mode Absoluut. - **Default layer and deep links:** `DEFAULT_STATE.dataset` is `woonscore`. The hash now carries `dataset=` when it is not the Woonscore, so a link to another layer keeps it; a hash without `dataset` opens on the Woonscore. Old links (which never had `dataset`) open on the Woonscore instead of Bevolking.

## 16 Nov 2026 — Onderwijsprestatie basisscholen: data and build (plan-onderwijsprestatie steps 1, 2 and the data part of 5)
- **Source and key.** DUO CKAN (`onderwijsdata.duo.nl`): `wporeferentieniveau-v1`, `wpo-eindscores`, `adressen_bo`; resource URLs looked up by `package_show` and file name. Key BRIN6 = INSTELLINGSCODE + VESTIGINGSCODE (the address file already has the BRIN6). Only `TYPE_PO = BO`; an address whose results are only SBO is left out.
- **Buckets.** Zero buckets are absent from the file (a subject usually has 2-3 rows), so absent = 0. `REKENEN_2F` (4.6k rows) counts as the target level like 1S. Several tests in one school-year (212 of 19k) are pooled: the buckets do not overlap.
- **Pupil total = eindscores leerjaar 8 only.** The file also has leerjaar-7 rows (often `-1`); including them broke the subtraction. A suppressed leerjaar-8 total makes the year total unknown.
- **Suppressed cells (`-1` = 1-4 pupils).** One hidden cell and a known total: total minus the rest when that is 1-4 (exact, 27k of 29k cases); outside 1-4 it is clamped and flagged. Two or more hidden cells: the remainder spread evenly when it fits k..4k, otherwise 2 each; always flagged (`estimate`). Deviation from the plan's "2 each": the remainder is the better estimate when the total is known, and the flag stays.
- **Schoolscore** 0-100 over all pupil results of 2022-2024 (below 1F 0, 1F 50, 2F/1S 100); `tested` = leerjaar-8 totals over the years (largest subject count when the total is suppressed); `small` < 30. `eduScore` = unweighted mean of school scores in the area; `eduFundPct`/`eduStreefPct` pupil-result-weighted.
- **Address → buurt.** CBS pc6huisnr 2023 (PC6 + leading house number) when that buurt code also exists in 2025, else the PDOK Locatieserver `buurtcode`; coordinates from PDOK for every school (address centroid, else postcode centroid). PDOK answers cached in `.cache/duo/pdok-geocode.json` (3 workers, 150 ms pause).
- **Schools near home (step 5, data only).** Per buurt from the PDOK 2025 `buurt_gegeneraliseerd` centre (`geoCentroid`, as the OV distances; centres cached in `.cache/duo/`): `eduNearScore` = mean score weighted by max(0, 1 − d/1.5 km), `eduNearBest` = best within 1 km, `eduNearCount` = scored schools within 1 km; null when nothing within 1.5 km. Wijk/gemeente: inhabitant-weighted mean of the buurt values (`buurten-2025.json` population), so `eduNearCount` there is an average, not an integer. App and wizard wiring: a later epic.
- **Two files instead of one** (the step-5 columns pushed one file to 1.75 MB, over the 1 MB target): `data/nl/onderwijs-po-2024.json` (0.75 MB; header, `levels.{buurt,wijk,gemeente}` = `{codes, cols}` in 2025 codes, 8 metrics, `schoolsFile`) and `data/nl/onderwijs-po-scholen-2024.json` (0.96 MB; `cols` column-wise: BRIN6, name, street, postcode, place, lat/lon, buurt, gemeente only where buurt is null, score, tested, estimate, fund/streef overall and per subject; no results → score null). `small` is not stored: it is `tested < smallN` (30). The pins load the second file only when switched on.
- **Build result (16 Nov):** 6,086 vestigingen, 5,977 scored (655 small, 3,300 with an estimated cell), 267 scored BRIN6 without an address (closed) left out; buurt found for 99.3% (pc6huisnr 5,824, PDOK 217, none 45), coordinates 6,085/6,086 (64 by postcode centroid). Rotterdam 168 schools, 165 scored, eduScore 73.9, eduNearScore 73.8. NL 2024 ≥1F / 2F-1S: lezen 98.5 / 73.4, taalverzorging 96.5 / 54.9, rekenen 92.5 / 43.2 (in line with the Inspectie's national picture; not compared figure by figure). 12,342 of 14,729 buurten have an eduNearScore.
